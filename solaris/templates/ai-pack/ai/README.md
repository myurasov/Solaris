## Quick Start

1. Open the project in your AI coding tool (Cursor, Claude Code, …) — the pack loads
   automatically through the root [`AGENTS.md`](../AGENTS.md) / `CLAUDE.md` shim.
2. First time on this machine? Say **"init project"** — the agent onboards your environment.
3. Describe your task. The agent plans, codes, and commits under this pack's rules.

## What This Is

An agent session starts at the project root's [`AGENTS.md`](../AGENTS.md), which points into
this folder. The pack then does three jobs: it defines the **engineer persona** the agent adopts
([`engineer.agent.md`](engineer.agent.md)), it carries the **project knowledge** the agent needs
(spec, instructions, memory), and it enforces the **working rules** — commit policy, safety, git
workflow, and the always-on rules in [`rules/`](rules/).

This file is generated and re-rendered when the pack updates, so put durable notes in
[`engineer.instructions.md`](engineer.instructions.md) instead of editing it. Files carry
Solaris sync metadata (`_Rev. N_` markers, the `revisions` map in `manifest.json`) — leave that
as-is.

## Configuration

Behavior switches live in [`defaults.json`](defaults.json) (committed, shared with the team); a
private `.memory/config.json` overrides them per key on this machine:

| Key | Default | Meaning |
|---|---|---|
| `git.developer_branches` | `true` | Everyone works on a personal `<id>-develop` branch; commits never land on `main` directly. |
| `git.feature_branches` | `true` | Larger features get their own `feature-<descr>` branch. |
| `subagents.level` | `auto` | How aggressively work is delegated to subagent models (`off`/`auto`/`quality`/`cost`). |
| `economy.level` | `med` | Token-frugality level (`off`/`med`/`full`/`auto`). |
| `yagni.enabled` | `false` | When on: deliver exactly what was asked, in the smallest coherent form. |

Machine-specific facts (hosts, URLs, accounts) go in `.memory/resources.md` — the init skill
fills them in; secrets only ever in `.memory/credentials.md` (gitignored). MCP servers are
configured in the project root's `.mcp.json` / `.cursor/mcp.json` (also machine-local).

## How-To

Each workflow below is a skill or rule the agent already knows — just say the trigger phrase.

### Start a Work Session

Open the project in your tool and describe what you want — nothing else to load, the pack wires
itself in. The agent answers questions directly, plans larger work first, and follows the commit
and safety policies automatically.

### Set Up a Fresh Checkout (init)

Say **"init project"** or **"onboard me"**. The agent collects the resources this project needs
(hosts, services — any can be skipped), writes the private `.memory/` layer, sets up your
personal git branch, and brings the environment up. Details:
[`skills/init.skill.md`](skills/init.skill.md).

### Run and Test the Project

Just ask — "run the tests", "start the app". The exact commands, conventions, and gotchas live
in [`engineer.instructions.md`](engineer.instructions.md), which the agent reads every session.

### Save and Resume Context

Say **"save context"** before stepping away: the agent snapshots the session into
`.memory/context.md`, and the next session picks up from there automatically.

### Stay Up to Date (refresh)

Say **"refresh"** or **"pull latest"**. The agent stashes your local edits automatically, pulls
`main`, rebases your personal branch onto it — resolving conflicts itself and asking only when
genuinely in doubt — re-applies your edits, migrates your local copy to any new layouts, and
reports what changed. It never pushes. Details:
[`skills/refresh.skill.md`](skills/refresh.skill.md).

### Work with Git

Per [`rules/git-collab.rule.md`](rules/git-collab.rule.md): you work on a personal
`<id>-develop` branch the agent creates automatically; commits there are automatic — single-line,
imperative; **nothing is ever pushed without an explicit ask**. To contribute back, ask for a PR.
Feature work goes on `feature-<descr>` branches and merges back with a merge commit when done.

### Release a Project Version

The project carries its own semver in the root `.version` file. The agent proposes a bump when a
milestone lands; say **"bump the project version"** or **"release the project"** to do it
explicitly (single-line commit plus a local `v<X.Y.Z>` tag).

### Manage Plugins

Under a Solaris checkout, "add plugin `<name>` to `<project>`" attaches one, and detaching
removes it — the [Attached Plugins](#attached-plugins) list above re-renders on the next sync.
A standalone checkout receives plugin updates through ordinary git pulls.

### Update the Pack Itself

Under a Solaris checkout, say "update `<project>`": Solaris syncs the pack's managed files
per-file (untouched files fast-forward, your improvements merge upstream, real conflicts ask)
and applies any framework migrations — this README re-renders with the current plugin list.
Standalone, just edit files normally and leave the sync metadata alone.

## Privacy: Memory, Logs, and Secrets

`.memory/` is the pack's private layer: `context.md` (session context), `resources.md` (your
machine's hosts and paths), `credentials.md` (secrets — never committed, never echoed),
`interactions.jsonl` (work log), `config.json` (per-machine switch overrides), and `spec-v0.md`
(the initial spec, captured at creation). It stays on your machine; everything else in this
folder is the shareable part of the pack.
