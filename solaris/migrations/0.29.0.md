## Summary

0.29.0 gives every project its own semver: a plain-text `.version` file at the project root (embedded
mode: the repo root), independent of `framework_version`, plugin versions, and the revisions sync
mechanism (no rev marker; `revs` never touches it). This migration seeds the file for an existing pack
and fast-forwards the pack files that document the bump-proposal workflow. Risk is minimal: one new
file plus doc fast-forwards.

## Pre-flight checks

- [ ] `ai/manifest.json` exists and is valid JSON.
- [ ] No `.version` file already exists at the project root (if one does, keep it - skip step 2).
- [ ] The project's `.gitignore` (when the root is in a git repo) does not match `.version` - it must be
      trackable.

## Migrate

1. `uv run -m solaris.tools.revs ff --dir projects/<slug>` - fast-forwards `ai/engineer.agent.md`
   (rev 38: the Project Version section) and `ai/skills/init.skill.md` (rev 8: seed-on-missing
   precondition).
2. Seed the version - ask the user which fits this project: adopt the repo's highest semver `v*` git
   tag if it has any, else `1.0.0` if the project has already shipped to users/partners, else `0.1.0`:
   `uv run -m solaris.tools.version project-set --dir projects/<slug> <X.Y.Z>`.
3. Optional: align the seeded manifest's `_comment` (it still says "no .version files") with the
   template rev-3 wording - "Framework + plugin versions live here; the project's own semver lives in
   the root .version file." The manifest is seeded-only (never materialized), so this is a hand edit;
   skipping it leaves a stale but harmless comment.
4. **When a git repo tracks the project root** (embedded packs always; some local-mode layouts keep the
   repo only in `source/`, and remote-code packs have no local repo - then the `.version` file itself is
   the whole record; skip this step): after `update-project` finishes its `version set --dir
   projects/<slug> 0.29.0`, commit everything this migration changed (the seed, the fast-forwarded pack
   files, and the manifest) in one single-line commit (e.g. "Add project version <X.Y.Z>"), and create a
   local tag `v<X.Y.Z>` on it - unless the version was adopted from an existing tag. Do NOT push the
   tag automatically - tag pushes follow the safety rule's confirm-first posture.

## Validate

- [ ] `uv run -m solaris.tools.version project --dir projects/<slug>` prints the seeded version.
- [ ] When the root is in a git repo: `git check-ignore .version` returns nothing, the working tree is
      clean after step 4's commit, and `git tag -l "v*"` lists the tag (unless adopted).

## Revert

1. When step 4 committed: `git revert` the seed commit (restores the pack files and removes `.version`
   in one inverse commit) and delete the local tag (`git tag -d v<X.Y.Z>`). Without a repo at the root:
   delete `.version` and restore the two fast-forwarded pack files from the previous framework version.
