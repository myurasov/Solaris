## Summary

Framework 0.49.0 adds a one-command update of a pack for releases that carry no framework migration, a mark for log
lines written by a session that manages a project from outside, lower bounds in the spend estimate, and revision
tracking of marked JSON files in a plugin's `shared/`. The bundled kaggle plugin (0.11.0) now requires the autocode
plugin. Below, `<pack>/` is the project's ai-pack folder and `<project>` its path from the Solaris root. A project
without the kaggle plugin only syncs files (steps 2 to 4).

- **`version update --dir <project> [--dry-run]`** brings a pack to the current release in one step: `revs ff`, the
  framework version, the version of each copied plugin that is behind, `revs baseline`, then its checks. It exits 3,
  changing nothing, when a file needs a merge, when a master does not match its ledger, or while a framework
  migration is on the way. This release has one (this file), so the steps below are done by hand this time. It is
  the one-step path for the patch releases that follow.
- **`interactions add --dir <project> --manager`** marks a line that a session managing the project from outside
  logs about it. `interactions who --dir <project>` lists such a line, labelled, and does not count it as work on
  the project.
- **`ai_spend`:** a request on a model with no price row is left out of the dollars, and every figure it belongs to
  is now marked as a lower bound (`>=` in the table, `at least $X` on the daily limit line, `lower_bound` in JSON).
  The exit code does not change, so the pack's token-economy rule (rev 7) says that exit 0 with an `at least` line
  is not a pass. Price rows were added for `claude-fable-5-2` and `claude-haiku-5-5`.
- **`revs`:** a plugin's ledger also tracks a `.json` file under `shared/` that carries an integer `"_rev"` field,
  so `revs ff` copies it into `<pack>/plugins/<name>/`.
- **Persona rev 54:** the housekeeping bullet names `linked_roots` (the key itself came with 0.47.0).
- **kaggle plugin 0.11.0** requires the `autocode` plugin: the master of a project that uses it runs only as an
  autocode agent. The hourly pass is the check of the master's hourly wake, outside reviews run through a sandboxed
  runner, a wait for a score is a watched job, a scan lists the open competitions, and autocode job definitions are
  kept as files in `<pack>/jobs/`. Its project steps are in `plugins/kaggle/migrations/0.11.0.md`.
- **autocode plugin 0.5.1** (rule rev 7, Start skill rev 2): a message that says it is from a manager agent is the
  manager's, and only the words it quotes as the owner's, with their date, are the owner's direction; the rule names
  the check for a job started by hand before the owner replaced a token; Start titles the session `@<agent id>`. A
  patch: it has no plugin migration.

## Migrate

1. With the kaggle plugin attached and the autocode plugin not: attach autocode first (`install-plugin`, "add plugin
   autocode to `<project>`"). kaggle 0.11.0 requires it, and `uv run -m solaris.tools.plugins check --dir <project>`
   exits 3 until it is there.
2. `uv run -m solaris.tools.revs ff --dir <project>` (the persona rev 54, the token-economy rule rev 7, and the
   files of every copied plugin).
3. `uv run -m solaris.tools.version set --dir <project> 0.49.0`. Then, for each copied plugin that
   `uv run -m solaris.tools.version check-plugins --dir <project>` reports as `behind`:
   `uv run -m solaris.tools.version set-plugin --dir <project> --plugin <name>` (it records the source's version:
   autocode 0.5.1, kaggle 0.11.0). A linked plugin records no version and needs nothing.
4. `uv run -m solaris.tools.revs ff --dir <project>` again (it renders the files that print versions), then
   `uv run -m solaris.tools.revs baseline --dir <project>`.
5. With the kaggle plugin attached: carry out `plugins/kaggle/migrations/0.11.0.md`. Steps 1 to 4 above did what
   that file asks for the pack's managed copies (autocode attached, the copy updated, the versions recorded and
   baselined), so do not run `version update` for it: it would stop, as said below. The rest of that file is for
   the project's master session, in a turn of its own.
6. With the autocode plugin attached: a running autocode session reads `<pack>/plugins/autocode/autocode.rule.md`
   (rev 7) again and titles itself `@<agent id>` with OpenCode's session rename. It reads the rule again by itself
   at its next start or compaction; tell it to now if it should act on the change at once.

**Later patch releases.** `uv run -m solaris.tools.version update --dir <project>` (with `--dry-run` first: the same
report, nothing changed) does steps 2 to 4 in one call and then runs its checks. It stops with exit 3, changing
nothing, while a framework migration is on the way, as with this release:
`uv run -m solaris.tools.version chain --dir <project>` lists the migrations a pack still has to run.

## Revert

With the kaggle plugin attached, read the Revert section of `plugins/kaggle/migrations/0.11.0.md` first: it says
what the master undoes and which of the plugin's files stay as they are. Then check out the masters of the release
the pack was on (0.48.5 at the latest), re-run `revs ff` and `revs baseline`, `version set` that version, and
`version set-plugin` for each copied plugin (autocode 0.5.0, kaggle 0.10.0). An autocode plugin attached in step 1
may stay: nothing reads it unless the session runs as an autocode agent.
