## What It Is

Kaggle for Solaris agents through the official Kaggle CLI (Kaggle's command-line client,
`github.com/Kaggle/kaggle-cli`) and six fixed, read-only reads through Kaggle's Python SDK for
what the CLI drops: a forum topic in full, the public notebooks with their scores, the
account's quota and runs in one read, the team's submissions with Kaggle's error text, a
dataset's version numbers, and a kernel's current version with the md5 of its source. A small
gateway script pins the CLI and installs it
separately into each project or ad-hoc task that uses it, never globally, and runs the SDK reads
in that same environment. A gateway skill (`kaggle-cli.skill.md`) routes agents to that script
and to Kaggle's own agent skill, vendored at the same version (the `kaggle-cli/` folder beside it;
upstream also names that skill `kaggle-cli`). An always-on rule keeps commands and every write on
the CLI and the SDK to those reads, every write to Kaggle owner-confirmed, and credentials out of
sight. Tools build on the gateway: a leaderboard history that saves every leaderboard read,
so competitors' progress can be followed over time (a read in which Kaggle served a page again is
marked unreliable and passed by), and the public notebooks' scores, so a
notebook jump shows; a discussions watch that lists a competition's forum, reads the new and
changed topics in full and prints them with the new comments marked; account sharing, which
splits one Kaggle account's sessions and weekly GPU hours between the projects using it (the
gateway refuses a kernel push that no sharing lease covers); one status page per project, the page
the owner reads (state with the outlook, the work tracks and the best-score lineage, leaderboard
progress against the top teams, plan, spending, resources with each machine's health, open
questions and suggestions, with live figures); a pre-submit check of what is new since
the last review, a gated submit that needs that check (the gateway refuses any other submit),
records a submit Kaggle refuses with Kaggle's reason and marks an unclear one that did land; a watch that
waits for one submission's score as a watched background job; an hourly pass that runs every read-only
check in one call, as the check of the master's hourly wake (through a small guard script, so that a tool
that cannot start never reads as a quiet hour), so that a quiet hour takes no turn: it flags
what needs a decision (board jumps, errored submissions with Kaggle's error text, unpushed commits, a master
off its allowed models or at another effort than the one the pack sets, spend limits, a peer project's
master that looks stopped, an older plugin copy, a stalled own line), holds back a flag that has not
changed and the news that can wait, and ends with a status block to paste into the status message; a
sandboxed, read-only runner for reviews by models of other families, with the review jobs kept as files in
the pack; a scout that lists the open competitions; and a
fetch of named files from a kernel output too large for `kernels output`. A playbook carries
the know-how for competing with an autonomous agent team, from the first hour to the final picks: a core read every
session, a skill per kind of contest, and a kernel-engineering skill read before building a submission.

The plugin requires the `autocode` plugin (`dependencies.required` in `manifest.json`). A Kaggle project's
master runs only as an autocode agent, an OpenCode 2 session: its wakes and their checks, the idle guard,
watched background jobs, compaction and reports to the owner follow that plugin's rule and Start skill. No
session clock runs, and no turn is owed by the hour.

## Files

| File | Role |
|---|---|
| `shared/tools/kaggle.py` | Gateway (`shared/tools/` holds the plugin's scripts): finds the project root (first; the nearest folder with exactly one child folder holding an ai-pack `manifest.json`, whatever that folder's name) or task folder, keeps `kaggle==2.2.4` + `kagglesdk==0.1.37` and a pinned `six==1.17.0` (which the CLI imports without naming it as a dependency) in `<context>/.venv-kaggle/` (created on the first call, rebuilt on a pin or package change, a folder move or a lost base Python, one install even under parallel calls; a venv built before `six` was added is rebuilt once) and execs it with the arguments unchanged; at the bare framework root runs the same pins from a throwaway uv environment. With `--sdk` first it runs `kaggle_sdk.py` in that same environment instead of the CLI, its output and exit code passed through. Inside a project or task two hooks run first and never block or change a command: an activity stamp for `kaggle_share.py` (`KAGGLE_SHARE_QUIET=1` skips it; an SDK read stamps as `sdk <read>`) and a tee that saves `competitions leaderboard` reads (what `--show` printed, the zip `--download` wrote) through `kaggle_lb.py` (`KAGGLE_LB_RECORD=0` turns it off; never for an `--sdk` read); at the bare framework root the tee runs only when `KAGGLE_LB_DIR` names a store. One gate blocks: `kernels push` (or `kernels update`; `k` for `kernels`) runs only while an open account-sharing lease covers the pushed kernel (`kaggle_share.py` `push_lease`: a lease of the project around the kernel folder naming that kernel or none; outside any project, one naming that kernel); otherwise it exits 3 before any install, stamp or Kaggle call with a one-line `acquire --path` hint, and it fails closed when the lease cannot be checked. `KAGGLE_SHARE_QUIET` does not bypass it; `KAGGLE_PUSH_WITHOUT_LEASE=1`, the owner's explicit override, does. A second gate refuses a bare `competitions submit` (`c submit`) the same way, with a one-line pointer to `kaggle_submit.py`: only that tool's own call (it sets `KAGGLE_SUBMIT_GATED=1`) or `KAGGLE_SUBMIT_WITHOUT_GATE=1`, the owner's explicit override, gets through; `KAGGLE_SHARE_QUIET` does not bypass it either. A submit that passes runs the same pinned CLI with one hook: when Kaggle answers a submit call with HTTP 400, 401, 403, 404 or 429 and an error message in the response body (the CLI prints only "400 Client Error: Bad Request"), it adds `kaggle gateway: Kaggle refused the submit (<status> <kind>): <message>` to stderr, from the body only (never a header or the request); the CLI's output and exit code are unchanged, and an SDK without the hooked client runs the plain CLI. Stdlib only; needs uv, found on PATH or else at `~/.local/bin/uv` or `~/.cargo/bin/uv`. |
| `shared/tools/kaggle_sdk.py` | The gateway's SDK reads, run only as `kaggle.py --sdk <read>` (it imports the pinned CLI's library and signs in as the CLI does): `topic <id>` (one forum topic in full: the opening post and every comment as Kaggle's HTML, links included, each reply nested under its comment; no profile paths, usernames or tiers; a `host` flag on the topic and each comment for an author the forum badges as a host, null until the pinned SDK carries the author type), `notebooks <slug> [--max N]` (up to N public notebooks, default 100, in Kaggle's score order, each with its best public score, null when unknown; `complete` false, with a note, when the list stopped short or a score could not be read), `account [--hours H] [--page-size N] [--done REF=TIME]` (the signed-in account's quota, one page of its own kernels, and the run state of up to 25 kernels run in the last H hours, default 12, skipping finished runs that `--done` names; in one process), `submissions <slug> [--page-size N] [--json]` (the team's latest N submissions, default 20, newest first, with ref, date, status, public score and the error text `competitions submissions` drops), `dataset <owner/slug> [--json]` (a dataset's current version number and every version with its number, date and notes, which the CLI does not show) and `kernel <owner/slug> [--json]` (a kernel's current version number and the md5 and size of its source, the bytes `kernels pull` writes, for any kernel the account may read; no source text is kept: it pins a fork to the version that was vetted). Read-only; topic, notebooks and account print one JSON document, submissions, dataset and kernel a few lines of text or, with `--json`, one JSON document; each read within a fixed call budget (one call for submissions, for dataset and for kernel). |
| `shared/tools/kaggle_lb.py` | Leaderboard history: `snapshot`/`show` save a gzip JSON snapshot per read under `<context>/__data/kaggle/<slug>/leaderboard/`, never overwritten, partial reads flagged, `--dir`/`KAGGLE_LB_DIR`; the page walk stops at a page that brings no new team and at a cap (`--max-pages N`, else the pages that the most teams of any saved snapshot fill, plus 5; 500 with none saved); a read is saved as `unreliable` (in the snapshot, with the count in `duplicates`, in its file name and in `index.jsonl`; an older index is upgraded once) when a whole page repeated teams read before, when 3 or more rows came twice (0.1% of the rows on a board of over 3,000 teams) or when it took far more pages than its rows fill, and every reader passes it by for the newest full snapshot that is reliable; fewer rows that came twice are the board moving during the walk, and that read stays a board with the count in `moved`; `history`, `movers`, `new-teams`, `summary`; `record-raw` and `tee_leaderboard` (the gateway hook); `import`; `notebooks` (the public notebooks with their best public scores, through the gateway's `--sdk notebooks`: one gzip JSON list per read in `notebooks/` beside `leaderboard/`, incomplete reads flagged, printed with new notebooks and score changes marked). Public leaderboard and notebook fields only. Stdlib only. |

| `shared/tools/kaggle_presubmit.py` | The pre-submit check: `<slug> [--vs SCORE] [--hours H] [--max-pages N]` runs `kaggle_forum.py check`, `competitions pages <slug> list <slug> --content`, `kaggle_lb.py notebooks` and `kaggle_lb.py snapshot` (read-only, unstamped) and prints what is new since the last review: host posts first and in full (hosts named in `presubmit/config.json`: `hosts`, `host_topics`; an author the forum badges as a host counts too, and a WARNING line names a badged author `hosts` lacks; `host mark: unknown` where no stored post carries an author type), new topics and comments (with no review yet, the last 24 h), pages added, changed or removed, notebooks new or re-scored (`--vs` marks those at or better), a new #1 and top-20 moves on the newest full snapshot that is not unreliable (`--max-pages` caps the board walk), then a TRIGGERS block (host post, rules or scorer, reported results, failure report, forum activity, page change, public notebook, notebook at or above `--vs`, board move, read failed, no review yet); exit 10 when any matched, else 0. `<slug> --ack` records exactly what the last check showed (no Kaggle call; a source whose read failed keeps its earlier view). Stdlib only. |
| `shared/tools/kaggle_submit.py` | The gated submit, a Kaggle write (`--go` only with the owner's approval of the printed command or a standing grant): `<record.json>` checks a submission record (`competition`, `file`, `message`; `kernel` and `version` in a code competition), its earlier attempts, the pre-submit check (at most `--fresh` minutes old, default 30, its findings acked) and the kernel run (`kernels status` COMPLETE), then prints the exact command; `--go --review "<one line>"` records the attempt, runs `competitions submit` once and records `submitted`, `refused` or `unclear`. `refused` only when the CLI failed and the gateway printed Kaggle's reason for an HTTP 400, 401, 403, 404 or 429 (`REFUSED BY KAGGLE: <reason>`, kept in the attempt's `reason`): nothing landed, so a later `--go` needs no `--checked`. `--landed <ref>` records an unclear attempt as landed, with no Kaggle call: the last attempt that is `unclear` or `submitting` becomes `submitted`, with `ref`, `was` and `marked` (exit 3 when nothing changed). One run at a time per record: a run holds a non-blocking flock on `<record>.lock` from before it reads the record to its end, and a second run is refused; the submit call alone carries `KAGGLE_SUBMIT_GATED=1`, the mark the gateway wants on a submit. Exit 0 submitted (or every check passed), 3 refused by the checks, 4 unclear: never retried; read the submissions (`--page-size 100`) and `submission-limits` first, then `--landed <ref>` when a row carries the exact message inside the attempt's time window, `--checked` when a clean read shows none (a failed or empty read decides nothing); 5 refused by Kaggle. Stdlib only. |

It schedules nothing; state in `<context>/__data/kaggle/<slug>/hourly/` (`last.json`; the receipts, kept 30 days, each with the pass's own submissions and account reads as `raw`, which an offline build of the status page draws from; the two locks; `status-build.log`). Private files (credentials, `.memory`, `AGENTS.md`, OpenCode and other agents' configs) are never copied. It uses the calling session's own provider key, read at run time from the session's OpenCode config and given to OpenCode only as `KAGGLE_REVIEW_KEY`; the prompt goes in on stdin. The runner never prints the key and never writes it to a file; where a provider's error repeats it, the runner cuts it from the output it keeps, and OpenCode's own log and session database go with the run's home. Before a model's first call, and again when the private config or the OpenCode binary changed, one call with an invalid key must be refused (HTTP 401 or 403), else nothing runs. The reviewer runs in its own process group, killed when it ends, at its time limit and at once when the runner is stopped. The review lands in `__out/review/<ID>/review.md` (`--out`), a failed run's text in `review.partial.md`, with `events.jsonl`, `stderr.log`, `copies.txt` and `run.json` beside it, and one line per run goes to the cost ledger `<pack>/.memory/spend.jsonl` (OpenCode's own estimate; category `outside reviews` by default). A review is there, and is not run again, when its file has text and its own `run.json` says a run for this ID wrote it and ended well, for the package as `READY` now names it; a new `READY`, or `--force`, runs it again, and the earlier review and record keep dated names beside it (`review-<day>.md`, `run-<day>.json`). A review has a time limit and a step limit, and no limit in dollars. Pack settings: `kaggle.review.model`, `.variant`, `.pool`, `.timeout`, `.max_steps` (150 model calls by default), `.session_config`, `.base_url`, `.category`, `.max_mb`. Project state under `__data/kaggle/review/`: the passed key gates, the gate calls' output and the records of runs in progress. Exit 0 the review is there (or the gate passed), 1 the run failed, 2 bad usage or bad input files, 3 the package is not ready, 4 no usable provider or key, 5 the sandbox could not be made safe, 6 the key gate failed, 143, 129 or 130 the runner was stopped by a signal; with `--pool`, the highest of the members' codes, a member killed by a signal counting as 1. Stdlib only; needs OpenCode 2. |

## Install

"install plugin kaggle to `<project>`" (copy) or "link plugin kaggle to `<project>`" (link
mode); for an ad-hoc task, add `kaggle` to its `Plugins:` line. Then sign in once per machine
(the `kaggle-cli` skill's Signing In section).

The plugin requires `autocode` (`uv run -m solaris.tools.plugins deps kaggle` prints the order: autocode,
then kaggle): `install-plugin` attaches it with kaggle, and `plugins check` names a pack that lacks it. The
`kaggle:competition` project type attaches kaggle, autocode and reporting. Autocode's own setup notes apply
(OpenCode 2.3.0 or later, connected to an autocode server): the gateway and the read-only tools also run in an
ad-hoc task or another session, but a competition's master runs only as an autocode agent.

Agents call the gateway from the project root or task folder (the `kaggle-cli` skill's Calling
the Gateway table has every context):

- copied install: `python3 <pack>/plugins/kaggle/tools/kaggle.py <args>`, where `<pack>` is
  the project's ai-pack folder (default `aipack/`, `ai/` in older projects, any name);
- linked install or ad-hoc task: `python3 <solaris>/plugins/kaggle/shared/tools/kaggle.py <args>`
  (from a grouped project root: `python3 ../../../plugins/kaggle/shared/tools/kaggle.py <args>`).

The other tools sit beside the gateway (`tools/kaggle_lb.py`, `tools/kaggle_forum.py`,
`tools/kaggle_share.py`, `tools/kaggle_presubmit.py`, `tools/kaggle_submit.py`,
`tools/kaggle_hourly.py` with its guard `tools/kaggle_hourly_check.sh`, which is the hourly wake's check,
`tools/kaggle_watch.py`, `tools/kaggle_scout.py`, `tools/kaggle_output.py`,
and `tools/kaggle_status.py`, `tools/kaggle_review.py` and `tools/kaggle_jobs.py`, which run
from a project root) and are called the same way. `tools/kaggle_sdk.py` runs only through the
gateway, as `<gateway> --sdk <read>`, since it needs the pinned CLI's environment. The job templates
are in `jobs/` beside `tools/`.

## Upstream and Upgrades

Pinned to CLI `kaggle==2.2.4` with the SDK it
was tested with (`kagglesdk==0.1.37`, which holds the auth/HTTP/API code), and Kaggle's
skill from the same tag (`shared/kaggle-cli/UPSTREAM.md` records the source and ref). The pins
are exact rather than `~=2.2.4`, so every project resolves the same tested CLI and the
vendored skill always matches it; patch releases arrive by moving the pin. The vendored files
are Kaggle's, under Apache-2.0. Move the pin as one change:

1. Set `PIN` in `shared/tools/kaggle.py` to the new release and `SDK_PIN` to the kagglesdk version a
   fresh install of it resolves to; keep `six` in `REQS`, pinned exactly (`SIX_PIN`), while the CLI imports it
   without naming it.
2. Refresh `shared/kaggle-cli/` from the matching tag (procedure in its `UPSTREAM.md`).
3. Update the version mentions in this README, the skills (`kaggle-cli.skill.md`,
   `how-to-kaggle.skill.md`), the rule and the manifest;
   `revs bump` the edited files and run `revs ledger`.
4. Test through the gateway, the `--sdk` reads included: `kaggle_sdk.py` calls the CLI's library
