# autocode 0.5.0 - A Guard With a Check, Watched Jobs, Start as a Skill <!-- omit in toc -->

- [Moved Paths](#moved-paths)
- [Pre-flight](#pre-flight)
- [Migrate](#migrate)

For packs updating from 0.4.0 or older (0.2.0 to 0.4.0 shipped without a migration and need no step of their own).
The idle guard gets a check, so an idle session with nothing open costs nothing; background jobs that must outlive
OpenCode are started through a tool that writes their end down and tells when one was lost; Start moves out of the
always-on rule into a skill; `wakes.py` knows zones. The rule now follows autocode 1.1.0-rc3. Nothing is breaking: a
session that changes nothing keeps working, with a guard that still costs a turn each time.

## Moved Paths

None: no file moved. Two parts of the rule did, and a pack's own text that names them is to follow (Migrate, 6):

- the rule's **Start** is now the skill `<pack>/plugins/autocode/autocode-start.skill.md`;
- the rule's **Shared resources** bullet is now "Hosts served by a fleet agent" in
  `<pack>/plugins/resource-sharing/resource-sharing.rule.md` (resource-sharing 0.4.1).

Two files are new in the copy (`autocode-start.skill.md`, `tools/guard.py`), and `guard.py` keeps a new private
folder, `<pack>/.memory/guard/`, which stays out of git with the rest of `<pack>/.memory/`.

## Pre-flight

- The project has this plugin copied at `<pack>/plugins/autocode/` (`<pack>`: the project's ai-pack folder). A
  linked plugin needs only steps 3 to 6, with the tools' real path in every call and in the guard's check:
  `shared/tools/guard.py` and `shared/tools/wakes.py` under the plugin root that the link file names
  (`<pack>/plugins/autocode/tools/` exists only in a copy, and a check whose script is missing fails quietly).
- The session runs as an autocode agent. Do the steps in a turn of that session, or tell it to: the wakes are
  set with its own tools.
- Find what names the old places: `grep -rn "autocode.rule.md\|Shared resources\|fleet agent\|nohup\|guard"
  <pack>/instructions.md <pack>/.memory/context.md tools/` (skip what does not exist), and `autocode_wake
  action=list` for the guard wake and any wake a project made to watch a background job.
- Where the resource-sharing plugin is attached, update it to 0.4.1 in the same go: it now holds the fleet agent
  bullet. A pack with autocode 0.5.0 and resource-sharing 0.4.0 has that bullet in neither rule. A project that
  asks a fleet agent for GPUs without resource-sharing attached copies the bullet into `<pack>/instructions.md`
  (its text: resource-sharing's rule, "Hosts served by a fleet agent"), or attaches that plugin.

## Migrate

1. Update the copy (`install-plugin` update): every `shared/` file of 0.5.0 into `<pack>/plugins/autocode/`
   (`autocode.rule.md`, `autocode-start.skill.md`, `tools/guard.py`, `tools/wakes.py`).
2. Read the new rule and the Start skill in the session (the copies it loaded before are stale).
3. **The guard.** `autocode_wake action=show name=guard`.
   - A guard without a check: set it again as the rule's Guard says (`idle 10m repeat`, check `python3
     <pack>/plugins/autocode/tools/guard.py check`, the rule's text; the same name replaces the wake).
   - A guard with a check the project made: keep it where it knows more than `guard.py` does, and have it also
     run `guard.py check`, exiting 0 when either finds something. A marker file of the project's own becomes
     `guard.py on <what>` and `guard.py off`.
   - Open steps kept as `- [ ]` lines in a file: name the file with `--steps`.
4. **Background jobs.** From the next job on, start work that must outlive OpenCode with `guard.py job start`
   (the rule's Background work). Jobs that run now, started as `nohup sh -c '<cmd>; autocode fire me <wake>'`,
   end as they are. A wake the project made only to check that such a job still lives can go once none is left.
   Move the job list out of `<pack>/.memory/context.md`: `guard.py job list` is the list.
5. **People-tied wakes.** `python3 <pack>/plugins/autocode/tools/wakes.py --dir . --zone <zone>` names, in its
   last line, the recurring events that were written with a local offset and are set as UTC crons: their local
   time moved by an hour when the clocks changed. For each that is tied to people, set its wake again as the
   line that `--local <name prefix>` prints (`cron "M H * * *" <zone>`); leave those tied to a clock elsewhere.
6. **The start prompt** recorded under "Autocode" in `<pack>/instructions.md`: point it at
   `<pack>/plugins/autocode/autocode-start.skill.md`. A prompt that still names the rule's Start works: the rule
   points on.
7. Record `{"name": "autocode", "version": "0.5.0"}` in `<pack>/manifest.json` (`version set-plugin`) and
   re-baseline the `revisions` entries for `<pack>/plugins/autocode/` (`revs baseline`).

## Validate

- `autocode_wake action=list` shows `guard` with its check. After the session was idle for its interval,
  `python3 <pack>/plugins/autocode/tools/guard.py status` shows a last check, and the wake's last 7 days show
  runs that its check skipped.
- `guard.py on test`, then an idle interval: the session is woken with "open work: test". `guard.py off` ends it.
- A short job (`guard.py job start --name try --wake try-done --deadline 5m -- true`, after setting the
  `fire-only once` wake `try-done`) wakes the session with "job try ended: exit 0", and `guard.py job done try`
  forgets it.
- The pre-flight grep finds no step that names the rule's Start or its Shared resources bullet.

## Revert

- First, while `guard.py` is still there: `guard.py job list`. A job that still runs ends by itself and fires
  its wake; wait for it, or stop it (`guard.py job stop <job>`).
- Then restore the 0.4.0 copy and the manifest entry from the plugin's git history, set the guard wake again
  without a check (`idle 90m repeat`), and delete `<pack>/.memory/guard/`.
